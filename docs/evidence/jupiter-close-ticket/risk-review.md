## Important findings

### F1 — Simulation hands the RPC usable close authority before the trigger and persisted send intent

- Primary location: `server/jupiterCloseTicket/reader.ts:429-438`.
- Calls establishing the window: `server/jupiterCloseTicket/bot.ts:338-345` and `bot.ts:360-368`.
- `simulate()` submits the entire owner-signed durable-nonce packet as base64 with `sigVerify: true`. Arm does this before the ticket becomes ARMED. Trigger does it before `store.claim()` persists SUBMITTING. This happens through the configured RPC, including a public endpoint, and arm does not require any enabled sender/live envelope.
- Reproduction: use an otherwise valid PREPARED ticket and exact owner-signed packet, configure a public RPC under the operator's normal read/simulation configuration, and call `arm`. The RPC receives valid signed bytes while the ticket is still PREPARED and there is no intent or approved trigger. A provider that broadcasts those same bytes can create the close request without the protected sender. This is a capability disclosure; an RPC advertised as read-only is technically able to relay it. The provider does not need the owner key. The same window exists during the pre-intent trigger simulation.
- Why blocking: default-disabled public sending, one intent before any possible submission, retained owner authority until the exact event, and encrypted persistence do not protect an authority already delivered to a third-party RPC. Ordinary trust in RPC account responses does not require giving it the ability to execute the ticket.
- Minimal fix: keep exact owner-signature/message verification local, simulate a signature-stripped serialization of the identical nonce-first message with `sigVerify: false` and `replaceRecentBlockhash: false`, and retain the original signed packet only for encrypted storage and the post-claim send. Prove locally that the simulation message hash is unchanged, all serialized signatures are unusable placeholders, and original send bytes remain exact. If a provider cannot perform that non-authorizing simulation, safely block before intent rather than disclose signed authority.
- Regression/evidence: capture the actual RPC request from arm and trigger and assert it cannot pass owner-signature validation and contains none of the original owner signature, while the exact message/nonce remains unchanged. Preserve wrong-signature-before-RPC and failed-simulation-before-intent checks. Rerun the native CLI path after the change because nonce simulation behavior is material.

### F2 — CLOSED lacks explicit evidence that this request actually decreased the position

- Primary location: `server/jupiterCloseTicket/bot.ts:249-261`; final admission at `bot.ts:473-499` and `bot.ts:155-161`.
- `keeperProof()` finds successful top-level `decreasePosition4` and `closePositionRequest2` instructions with pinned addresses, then proves a positive request-ATA-to-recipient SPL transfer and recipient balance increase. It does not decode an actual decrease event/state result or the close event's `executed` flag. Reconciliation separately reads a later finalized zero-size account. Thus the required actual-reduction correlation is inferred from instruction appearance rather than represented in the accepted evidence.
- Reproduction of the predicate gap: `server/jupiterCloseTicket/reconciliation.test.ts:93-124,127-132` deliberately constructs success metadata with correctly addressed instruction bytes and positive payout but no `DecreasePositionEvent` or executed-close provenance; the test expects `keeperProof()` to return true. `bot.test.ts:267-309` even admits a constructed same-transaction close-before-decrease ordering. These synthetic cases demonstrate the predicate's insufficiency, not a claim that such a no-op or impossible ordering was observed at Jupiter.
- Why blocking: the approved gate explicitly requires correlated keeper evidence and forbids using an unrelated later zero as proof of this ticket's closure. The public shape sample proves v0/ALT/split transport only. It does not establish a protocol guarantee that every successful addressed `decreasePosition4` is a positive entire-position reduction. Without a transaction-bound decrease result, the implementation cannot independently establish the promised correlation. The no-manual-close/reopen promise reduces races; it is not permission to infer missing outcome evidence.
- Minimal fix: require authenticated Jupiter-origin event or equivalent transaction-bound state evidence for the actual positive close reduction, bound to the exact request, target, owner, pool/custodies and original position lifecycle. The pinned IDL already describes `DecreasePositionEvent` including `sizeUsdDelta`, `positionSizeUsd`, `positionRequestKey`, target/custodies and `positionOpenTime`, and `ClosePositionRequestEvent` including `executed`, `entirePosition`, request, owner/mint and amount. Verify the relevant field semantics, reject a zero/no-op/unexecuted/mismatched event, preserve the exact positive SPL payout proof and finalized same-position zero, and correlate ordered split receipts. Attribute events to the actual Jupiter invocation/CPI context rather than accepting arbitrary lookalike log text. Missing event/state coverage remains UNKNOWN.
- Regression/evidence: no actual-decrease evidence, zero delta, unexecuted/cancel close, wrong request/lifecycle, spoofed event origin, and impossible ordering must remain UNKNOWN/false despite positive recipient balances and a later zero. A correctly correlated actual reduction and executed payout may pass synthetic contract tests; such tests still do not prove provider acceptance.

### F3 — The documented disable then nonce-revoke confirmation path cannot complete

- Primary location: `server/jupiterCloseTicket/bot.ts:508-511` and `server/jupiterCloseTicket/store.ts:154-169`.
- Documented user path: `docs/jupiter-close-ticket.md:42-44`.
- The guide tells the operator to disable the ticket, separately advance its nonce, then call `confirm-revoke`. Disable persists DISABLED, but confirmation immediately rejects every status except ARMED. The store likewise has no DISABLED-to-REVOKED transition. The final observation never happens even after a real finalized nonce change, and the CLI returns a generic COMMAND_REFUSED.
- Reproduction: start with unused ARMED, run `disable`, independently change the dedicated nonce, run `confirm-revoke`; it fails at line510 before any RPC read. A fake finalized reader/state fixture suffices to reproduce this local state defect; no live action is needed.
- Why blocking: this is the actual documented operator recovery flow. Users should be able to locally stop an unused ticket first and then record the distinct cryptographic revocation. The current implementation preserves safety by refusing, but leaves the advertised recovery path incomplete and obscures whether the external revoke was observed.
- Minimal fix: allow confirmation for unused ARMED or DISABLED tickets with no persisted send intent, perform the existing finalized genesis/nonce observation, and atomically persist REVOKED. Add the narrowly permitted DISABLED-to-REVOKED transition with the no-intent constraint. Do not re-enable, resend, reset pending statuses, or confuse nonce revoke with request cancellation. A narrower documentation-only alternative must clearly describe independent mutually exclusive paths, but supporting the already documented safe combined sequence is preferable.
- Regression/evidence: ARMED-to-DISABLED-to-observed-REVOKED succeeds after finalized nonce change; unchanged nonce and all SUBMITTING/UNKNOWN/REQUEST_PENDING cases reject. Keep disable alone explicitly local-only.

## Minor observation

`scripts/jupiter-close-ticket.ts:181-188` reserves a PREPARED DB row before exclusively writing the unsigned output and printing its ID. An existing output path, filesystem error, or crash after the INSERT can leave a PREPARED reservation with no CLI-visible ID, and a retry is refused by uniqueness. A later small improvement can check the output path before reservation and provide a safe public-ID recovery/status lookup without resetting nonce reservations. This is not part of the blocking send/closure findings.
